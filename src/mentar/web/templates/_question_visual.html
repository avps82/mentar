{# The picture that BELONGS to the live question (visual-first, 2026-08-21). Sits BELOW the question text (maintainer, 2026-08-21: "Feel like the question should be above the diagram?"). It read as a context-free block of art at the top of the bubble -- a child's eye landed on four rows of stars with no idea what they were for, and had to read DOWN to find out, then look back up. Instruction first, then the material, is how a worksheet reads. It also puts the picture next to the answer box, which is where a child is looking while they count. Sits as a SIBLING of .question-text, never inside it, for two reasons: * tts.js reads .question-text's textContent, so the app's own read-aloud can never try to speak ASCII art -- that silence is structural, not a filter that can rot; * .question-text is pre-wrap but a PROPORTIONAL font (measured in chromium: rows break, columns do NOT align), which is exactly what this 
 fixes.

   Uses .ascii-art, NOT .steps-pre: .steps-pre is overflow-x:hidden, safe only
   because the step grid's width is computed to fit. A question picture has no
   such guarantee, and silently CLIPPING a picture the question depends on is the
   worst available failure. Both classes already share one diagram-box surface.

   Deliberately NO aria-hidden and NO aria-label. aria-hidden would declare the
   picture DECORATIVE, which is false -- it is the question. An aria-label would
   have to describe it, and any accurate description states the answer ("a bar
   with 1 of 5 parts shaded" IS 1/5). So a constitutive visual question is not
   screen-reader answerable, and that is recorded as a real limitation in
   docs/design/visual_first_gap.md rather than papered over with markup that
   claims otherwise.

   Autoescaped by Jinja, no `| safe` -- computed content, same trust boundary as
   the mc4 radios and the step grid. #}
