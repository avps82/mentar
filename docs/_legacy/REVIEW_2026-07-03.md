## 1. SAFETY-CRITICAL — spec claims controls that don't exist in code

These matter more than normal doc drift because SAFETY.md is the document a safeguarding
reviewer (and any parent reading the repo) will audit against.

### 1.1 SAFETY.md §1.5.2(2) promises an injection strip step; the code deliberately doesn't strip
- **Issue:** SAFETY.md L1 §1.5.2 mitigation 2 states (present tense) that "a pre-processing step
  scans retrieved passages … flagged lines are (a) **stripped** from the grounding passage before
  it reaches the LLM, and (b) **logged** … for parent review."
  `src/mentar/grounding/wrapper.py` does the opposite by design: "This module does NOT strip,
  filter, or interpret the passage … Stripping 'suspicious' strings here would be security
  theatre." The W7 design contract superseded the SAFETY.md mitigation but SAFETY.md was never
  updated. Neither stripping nor the promised *logging/flagging* of imperative lines exists.
- **Recommendation:** update SAFETY.md §1.5.2 to describe the actual control (data-wrapping via
  `<<<GROUNDING_BEGIN/END>>>` markers + scope constraint), and either add the cheap *flag-and-log*
  half (detection without stripping — no content-corruption risk, gives the parent audit trail) or
  explicitly record its removal with rationale. A safety spec that overstates shipped controls
  fails its own audit-trail purpose.

### 1.2 escalation_log is missing fields SAFETY.md says are recorded
- **Issue (a) — severity:** SAFETY.md §3.5 states "v0.1 records a `severity` per trigger but does
  not branch flow on it — data only, for Bucket D." No `severity` column exists in
  `src/mentar/db/schema.sql` (escalation_log) and the controller never persists it. Bucket D will
  not have this data.
- **Issue (b) — session id / turn number:** SAFETY.md §3.3 Step 2 says the escalation log entry is
  "timestamped, session ID, turn number, trigger category." escalation_log has no `session_id`
  and no turn number — an escalation can't be joined to its session/transcript position.
- **Issue (c) — `session_outcome` is wrong for jailbreaks:** schema comments require
  `'logged_only'` for `adversarial_jailbreak`, but the live path
  (`controller._step_core` → `_DbStoreAdapter.write_escalation` → `LearnerStore.write_escalation`)
  never sets `session_outcome`, so every row — including LOW jailbreaks that did **not** freeze
  the session — is stored with the default `'frozen'`. The audit log misstates what happened.
  (Only the demo helper `escalation.handle_trigger()` sets it correctly, and nothing calls it.)
- **Recommendation:** schema v2 migration adding `severity`, `session_id`, `turn_index`; extend
  `write_escalation(...)` to take severity + outcome; delete or de-duplicate `handle_trigger()`
  (two parallel escalation write paths = guaranteed drift — it already drifted).

### 1.3 Retention/purge (SAFETY.md §4.6, SECURITY.md) is documented as applied but unimplemented
- **Issue:** SECURITY.md: "a rolling retention window **is applied** at the application layer."
  schema.sql: "Retention policy (90-day default …) is enforced at the application layer
  (LearnerStore)." `LearnerStore` contains no retention, purge, or deletion code of any kind
  (grep: zero hits in `src/`). Note the transcript immutability triggers as written
  (`RAISE(ABORT)` on any DELETE) also make a future row-level purge impossible without a schema
  change — retention and immutability are currently mutually exclusive designs.
- **Recommendation:** decide now (it affects schema): either (i) time-boxed trigger exception /
  purge path designed alongside immutability, or (ii) reword all three docs to "planned, not yet
  implemented; pilot retains everything; deletion = delete the .db file." Don't ship docs that
  claim active data-minimisation to parents when there is none. [⚠️ Verify — retention wording
  has compliance weight under COPPA 2025 / GDPR-K.]

### 1.4 Escalation freeze hands the resume control to the child's screen
- **Issue:** on escalation, `web/app.py:/answer` **redirects the child's browser to `/parent`**,
  which shows (on the same screen, same session, no auth): the full escalation log **including the
  verbatim trigger text** and the acknowledge/resume control (`/parent/ack` POST, no PIN, no
  confirmation). SAFETY.md §3.3 Step 4 explicitly says the alert must NOT carry the verbatim text;
  the honor system is documented, but the current flow doesn't just *fail to prevent* the child
  resuming — it actively navigates them to the button.
- **Recommendation (cheap, pilot-appropriate):** on escalation redirect the child to a static
  frozen page showing only the two fixed handoff messages; keep `/parent` reachable only by typed
  URL; require a typed confirmation word on `/parent/ack`. Full PIN gate stays Phase 1.

### 1.5 Session-start AI-transparency statement (SAFETY.md §5.5) not implemented
- **Issue:** §5.5: "At the start of each session, Mentar presents a brief age-appropriate
  statement that it is a computer learning helper, not a person." The only deterministic
  session-start line is `ASSENT_LINE` ("you can stop anytime"). AI disclosure exists only
  reactively in the system prompt ("if the child asks, say so").
- **Recommendation:** one-line fix — extend the first-turn preamble in `controller.step()`:
  assent line + "I'm Mentar, a computer learning helper — not a person." Deterministic, testable,
  closes a stated Layer-5 requirement.

### 1.6 No output-side safety gate exists (added 2026-07-03, follow-up pass)
- **Issue:** SAFETY.md Layer 2 §2.1/§2.2 promise that hard-block matches are *discarded and
  incident-logged* and that every generated output is *checked for topic scope,
  age-appropriateness and pedagogy before delivery*; ARCHITECTURE.md §2 states "all generated
  output passes through the safety layer before reaching the child." The actual LLM output path
  is `llm_call → redact_credentials → _strip_trailing_questions → child` — no content check, no
  scope check, no discard path, no incident log. Output safety is prompt-instructions only.
- **Recommendation:** deterministic `safety/output_guard.py` chokepoint inside `_make_safe_llm`
  (same pattern as the credential guard): v0 blocklist + scope heuristic + incident log row +
  neutral redirect on discard. Gives Bucket E a landing place and makes the Layer-2 claims true.

### 1.7 Help explanations are never verified — only child answers are (added 2026-07-03)
- **Issue:** SAFETY.md §6.2 Level 2 promises numeric computations *in re-explanations* are
  computationally verified before serving, with failing explanations discarded and regenerated.
  `verify_numeric.check()` is only ever called on the child's answer (`_do_score`,
  `_do_help_recheck_score`, `_do_probe_score`). A Help explanation containing a wrong worked
  step ships unchecked — against the project's own "hallucination = safety failure" bar.
- **Recommendation:** in `_do_help_explain`, extract `a <op> b = c` steps from the explanation,
  verify with the existing verifier, regenerate on failure (bounded by the existing retry cap),
  fall back to `_fallback_hint` if still failing.

## 2. CORRECTNESS / PEDAGOGY BUGS (not yet in the known-defects register)

### 2.1 System prompt is hardcoded to fractions/Year-4 but the app now serves 3 subjects
- **Issue:** `prompts/system_prompt.md`: "You help the child learn **fractions** at a Year-4
  level… Stay within fractions / Year-4 maths." The web app (2026-06-29) added `arithmetic` and
  `science` subjects that use the same system prompt for every LLM call (Help explanations,
  fallbacks). For science, the model is instructed to stay within fractions while being asked to
  explain animal classes — an internal scope conflict that degrades Help quality and muddies the
  Layer-1/2 scope guarantee the prompt is supposed to anchor.
- **Recommendation:** parameterise `{{subject}}` / `{{scope_line}}` in the system prompt (keep it
  a versioned template; re-hash in the registry), source it from the active curriculum template's
  `subject:` field.

### 2.2 `help_pressed` signal for false-confidence classification is wrong in two ways
- **Issue:** `controller._do_probe_classify` passes
  `help_pressed=len(ctx.help_modalities_used) > 0`. (a) `help_modalities_used` is only reset when
  a *new* Help cycle starts — it carries over from the **previous node**, so a probe on node B
  after Help on node A sees `help_pressed=True` and can misclassify a true `false_confidence` as
  `slip_suspect` (SPEC §14.4 defines the condition as "no Help pressed **on concept**"). (b) Since
  auto-help-on-wrong landed (note 4b), the flag is also set by *system-initiated* scaffolding, not
  only child-declared confusion — conflating exactly the signal §14.1 says must be kept distinct.
- **Recommendation:** track `help_by_node: dict[node_id, child_initiated: bool]`; pass
  per-node, child-initiated-only. Small change, protects the project's core metric (the
  false-confidence rate is a named pilot goal, SPEC §23).

### 2.3 Web learner identity is not durable — every server restart silently resets mastery
- **Issue:** `web/app.py` keeps `_db_learner_ids` in memory only. The `learner_uuid` cookie
  survives a restart; the mapping doesn't, so `_get_or_create_controller` calls
  `store.create_learner(...)` again → a **new** learner row per restart, orphaning all prior
  skill_state/transcripts under the old id. Contradicts SAFETY.md §4.3 ("BKT state retained until
  parent resets/deletes") and quietly breaks pilot continuity (mastery restarts at P_L0; the
  parent sees an empty history).
- **Recommendation:** look up the learner by the deterministic name (`pilot-<uuid8>`) before
  inserting, or persist the uuid→id map in a table. Also gives the parent view a stable history.

### 2.4 Legacy LLM-question fallback still scores against a question, not an answer
- **Issue:** `web/app.py:_load_curriculum` sets `expected_answer = transfer_seeds[0]` (a question
  string). Any node not covered by a bank/generator falls back to LLM-generated questions scored
  against that string — guaranteed FAIL/SAFE_REJECT. Known from 2026-06-18 as a design gap, but it
  was left in place silently rather than guarded.
- **Recommendation:** if no item source covers a node, refuse loudly at startup (config error)
  instead of silently mis-scoring. One assertion in `_load_curriculum` or controller init.

### 2.5 Unreadable-answer loop has no exit
- **Issue:** `_do_score` on SAFE_REJECT/EXTRACT_FAIL re-asks the same question forever. A child
  who genuinely can't produce the expected shape (e.g. keyboard trouble, misunderstanding `_/_`)
  is stuck in an infinite nudge loop with no scaffolding.
- **Recommendation:** after 2–3 consecutive extraction failures on the same question, route into
  the Help loop (unscored) — consistent with the auto-help-on-wrong philosophy.

### 2.6 Grounding likely collapses to one short passage for 7 of 8 pilot nodes
- **Issue:** all fraction nodes except `whole_number_division` anchor to the same Vikidia
  `Fraction` article, whose verified lead extraction is ~216 chars. `passage_hint` *is* consumed
  (`reader.get_section` does heading-word matching), but hints like "Equal parts requirement —
  why fractions need equal-size pieces" only differentiate if the short Vikidia article has
  matching section headings — otherwise every node falls back to the same ~216-char lead. So
  Level-1 grounding — "the biggest single risk drop" (SPEC §15) — is plausibly near-identical
  generic text for comparing, adding, subtracting, equivalence, etc. REMAINDER_PLAN B1 covers
  thin-anchor re-pointing but not this granularity question.
- **Recommendation:** run the B1 per-node extraction report and check *distinctness* as well as
  length (log which section each hint resolved to); where hints don't hit a heading, author
  per-node passage text in the template or split anchors across Vikidia/Simple-WP articles.
  Otherwise accept and document that pilot grounding is nominal for most nodes.

- **Issue:** no `.github/` — the "pytest green + ruff clean" gate is convention only. For an OSS

  Distributing artifacts before the licence text is in place is legally sloppy for an OSS project.
- **Recommendation:** paste the text (it's a 2-minute maintainer job flagged since 2026-06-27);
  treat as a hard pre-public blocker. Consider deleting the checked-in-adjacent `dist/` artifacts

### 3.4 Live credential on disk + unrotated token
- **Issue:** `eval/.creds.env` (gitignored, correctly untracked) holds a live-looking token, and

## 5. ARCHITECTURE OBSERVATIONS (decisions, not defects)

- **Session state is process-memory only.** A `mentar serve` restart mid-session loses FSM
  state (transcript survives; the session doesn't resume — compounded by 2.3). Fine for the pilot
  if stated; SAFETY/README don't state it. Options: (a) document one-shot sessions as a pilot
  constraint; (b) persist minimal FSM context per session row.
- **Two escalation write paths** (controller inline vs `handle_trigger`) — consolidate (see 1.2c).
- **BKT rising-mastery-on-wrong** — the register's Option B (gate `learns` on non-wrong
  observations) is the right call for a parent-facing number; classic-BKT purity isn't worth the
  parent mistrust, and the demote-on-probe patch already deviates from classic BKT anyway.
- **`_strip_trailing_questions`** drops *any* trailing line containing "?" — it will occasionally
  eat a legitimate final line of explanation prose. Acceptable trade; worth a code comment that
  it's lossy by design.
- **Flask dev server in production-ish use** — `app.run()` + threaded Werkzeug is fine for
  localhost pilot; note it (waitress is a one-line swap in Phase 1 if the service-ification
  backlog item lands).
- **No CSRF tokens / default `SECRET_KEY`** on the web forms — irrelevant on localhost single
  family; must be revisited before any LAN/multi-device use (a LAN-exposed `/parent/ack` with no
  auth would be a real safety hole given 1.4).

## 8. SECOND-PASS FINDINGS (2026-07-03, follow-up architecture sweep)

All verified against source; promoted to PHASE0_STATUS defects / REMAINDER_PLAN A15–A19.

### 8.1 Escalation logging is best-effort — "never silently dropped" can be violated
- **Issue:** the controller wraps `write_escalation` in try/except with only a `logger.warning`.
  On DB failure the session still freezes, but the verbatim disclosure is lost — violating
  SAFETY §3.1 principle 2. Best-effort is right for tutoring logs, wrong for escalations.
- **Recommendation:** fallback sink — on DB write failure, append `{ts, class, severity,
  verbatim}` to an append-only local file (e.g. `~/.mentar/escalation_fallback.log`) and surface
  a parent-view warning that durable logging degraded.

### 8.2 Curriculum templates are never validated at runtime → false "all mastered" message
- **Issue:** `validate()` only runs via the explicit `mentar validate-template` subcommand;
  `serve`/`run-session` parse the YAML directly. A cyclic or bad-prereq template makes nodes
  unsatisfiable → `outer_fringe` returns empty → NODE_SELECT tells the child *"Well done —
  you've mastered all the concepts!"* — a silent false completion.
- **Recommendation:** run validation at startup for every loaded template; refuse to serve on
  failure, naming the template and error.

### 8.3 Layering violation: CLI imports the web module
- **Issue:** `cli/__main__.py` imports `_load_curriculum` + `_DbStoreAdapter` from
  `mentar.web.app`. Headless `run-session` therefore requires Flask, and the import executes
  `web/app.py`'s module-level side effects (Flask app creation, loading all subject curricula).
- **Recommendation:** move curriculum loading to `engine/curriculum.py` and the store adapter to
  `db/`; web and CLI both consume them. Also removes the duplicated-loader drift risk.

### 8.4 Prompt changes don't invalidate the safety-eval result (process gap)
- **Issue:** the "pipeline safety 20/20" validation (2026-06-27) ran against that day's
  `system_prompt.md` + help templates; the templates have been edited and re-hashed several
  times since. The hash registry detects change but nothing requires re-running the adversarial
  suite, so the headline safety claim silently ages.
- **Recommendation:** rule in AGENTS.md/CONTRIBUTING + (once A12 lands) a CI warning: any
  `prompts/*.md` hash change ⇒ re-run T1.5 adversarial through the pipeline before merge, note
  the run date next to the claim in EVAL_RESULTS.md.

### 8.5 English-only safety layer vs. the per-country product claim
- **Issue:** all 61 trigger regexes, the fixed handoff messages, feedback pools and hints are
  hardcoded English. A non-English child's distress disclosure fires nothing. Fine for the
  pilot; structurally, the per-country/per-language curriculum claim has no safety counterpart.
- **Recommendation (design, post-pilot):** language becomes a first-class gate — loading a
  template in language X is refused until a vetted trigger bank + handoff wording for X exists.
  Record in SAFETY.md as a known scope boundary now (one paragraph).

### 8.6 `age_mode` is stored but never read
- **Issue:** schema + SPEC define parent-mediated vs independent; no code branches on it.
  A load-bearing SPEC concept with zero enforcement hook.
- **Recommendation:** startup assertion (pilot supports `parent_mediated` only) so the gap is
  explicit and greppable; real branching arrives with the Phase-1 PIN work.

### 8.7 Smaller improvements
- **No dependency lockfile** — floating `pyyaml>=6.0`, `openai>=1.0`; add a constraints file /
  uv lock, pairs with CI (A12).
- **Unseeded `random`** in the controller — per-session seeded RNG (logged) makes pilot sessions
  replayable for debugging.
- **`.vendor/` PyYAML duplicates the pyproject dep** — document precedence or drop the vendored
  copy once CI guarantees installs.
- **No backup tooling** — "export = file copy" requires a WAL checkpoint first; a
  `mentar backup` subcommand (checkpoint → copy → verify) makes the parent-facing story real.

### 8.8 Invariant to protect (strength, not a gap)
**Child input never reaches the LLM.** It is routed and scored deterministically only — which is
why child-driven prompt injection is structurally dead in this architecture. The
INTERACTION_SCOPE proposal will be tempted to relax this; the invariant should be named in
AGENTS.md RULES and in that design doc before any build.
