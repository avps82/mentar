# W6.3 — Pilot Interface Decision

**Question:** What surface does the child see in the Phase-0 pilot? Decision only — building
it is Phase-0 build work, not this task.

**Input:** W3.5 verdict = **reference-only**, so option (c) "fork an existing skeleton" is
off the table.

## Decision: **(b) Minimal local web app** — Flask/FastAPI + 4 plain HTML views

Rejected: **(a) TUI** — fastest to build, but the weakest surface for an ~8–9-year-old
(typing-in-a-terminal is unfamiliar and intimidating; no room for the simple visual
framing the Help modalities assume) and it gives the parent a poor review surface.

## Why a minimal web app

- **Right for the learner.** A browser page renders the visual/concrete Help modalities
  (SPEC §13.2) far better than a terminal, and is a surface a child recognises.
- **Right for the parent.** Parent-mediated mode (SPEC §6.2) and SAFETY Layer 5 need a
  reviewable transcript/log surface and a visible escalation alert + acknowledge control
  (SAFETY §3.3 Steps 4 & 6). A web view delivers these cleanly; a TUI does not.
- **Still local-first.** Flask/FastAPI bound to `localhost` keeps everything on-device — no
  hosting, no data egress (SPEC §17.2). Plain server-rendered HTML, no SPA, no build chain.
- **Cheap and disposable.** Four static-ish views over the existing engine/FSM; no
  framework lock-in. The pilot UI is explicitly throwaway (real UX is Phase 1, SPEC §4.1).

## The 4 views (map to the session FSM)

| View | Purpose | FSM states served |
|------|---------|-------------------|
| 1. **Learner question screen** | Present concept/problem + answer input | `PRESENT`, `AWAIT_ANSWER`, `SCORE` |
| 2. **Help pop-up** | Re-explanation in a different modality + mandatory transfer re-check | `HELP_REEXPLAIN`, `HELP_RECHECK*` |
| 3. **Probe interrupt** | Non-skippable proactive probe | `PROBE_PRESENT`, `PROBE_AWAIT_ANSWER` |
| 4. **Parent log view** | Transcript review + **escalation alert flag + "Acknowledged — resume" control** | `ESCALATION_FREEZE` → `PARENT_ACK_WAIT`; review of all logs |

View 4 is load-bearing for safety: it surfaces the SAFETY §3.3 parent alert and is the gate
for resuming a frozen session (parent physically present, presses acknowledge).

## Constraints for the build (carry-forward, not built here)

- Bind to `localhost` only; no external network calls from the UI layer.
- Non-skippability (T5.1): views 2 and 3 must not allow advancing without a scored answer
  (enforced server-side by the FSM, not just the UI).
- Prompts come only from `prompts/` templates via the controller (W6.2) — no UI-side prompt text.
- Stack choice (Flask vs FastAPI) is a build-time detail; both satisfy this decision.
  Recommendation: **FastAPI** (async-friendly for streaming model output later) unless the
  builder prefers Flask's simplicity for 4 static views.
