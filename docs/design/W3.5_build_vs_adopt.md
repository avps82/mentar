# W3.5 — Build-vs-Adopt Assessment: Open TutorAI

**Question (W3.5):** Can Open TutorAI's modular learner/parent interface skeleton be
**forked** as Mentar's dialogue framework, or is it **reference-only** (like OATutor)?

> ⚠️ **Desk assessment.** This sandbox has no network access, so I could not clone, run, or
> read Open TutorAI's current source. The verdict below is reasoned from the project's own
> principles (SPEC §19.1, §4.1) and the public characterisation in SPEC §19.2. **Confidence:
> medium.** §5 lists exactly what a 1-day hands-on spike must check to firm it up.

## Verdict: **REFERENCE-ONLY** (do not fork)

Treat Open TutorAI the same way SPEC §19.2 already treats OATutor: study its modular
interface boundaries (learner / educator / parent separation) as an architectural
reference, but **build Mentar's dialogue framework and surface ourselves**.

## Rationale

1. **The differentiator is the part you can't inherit.** SPEC §4.1: Mentar's bar is
   *safety + pedagogy + local-first*, and §19.1 puts the owned/novel share at ~60%
   (curriculum templating, integrated kid-safety, the LLM questioning engine,
   critical-thinking measurement). A forked UI skeleton is the cheap ~40%; it does not move
   the hard 60%, and our safety layer (SPEC §16) must permeate *every* surface — retrofitting
   that into someone else's interface assumptions is usually costlier than building 4 plain
   views ourselves.

2. **Stack mismatch.** Mentar's engine is Python (pyBKT, KST port, verifiers, SQLite store)
   and local-first. Adopting a research-stage web/JS app would split the stack and the
   build's mental model, and complicate the no-data-leaves-the-device guarantee
   (SPEC §17.2). The pilot surface needed is tiny (W6.3: ~4 views).

3. **Maturity risk.** SPEC §19.2 files Open TutorAI under "LLM-native (watch,
   research-stage)" — "closest to our vision" but not a stable base. Forking research-stage
   code imports its churn, its assumptions, and its safety posture (which we'd have to audit
   line-by-line anyway, given §16).

4. **The principle already decided this for OATutor.** Nothing about Open TutorAI changes
   the §19.1 stance that OSS is "borrowed plumbing, not the spine." Reference-only keeps us
   free to take its best *ideas* (the clean learner/educator/parent module split is worth
   imitating) without inheriting its code.

## Consequence for downstream tasks

- **W6.3 (pilot interface):** option (c) "fork an existing skeleton" is **ruled out**. The
  decision is between (a) TUI and (b) minimal local web app. See `docs/design/W6.3_pilot_interface.md`.
- **What to borrow as reference:** the learner / educator(parent) interface *separation*,
  and any clean mastery→content wiring (alongside OATutor's, per §19.2).

## §5 — What a hands-on spike should confirm (to lift this from provisional)

1. Licence (permissive enough to fork? compatibility with our eventual W4.2 choice).
2. Language/stack and whether the "modular interface" is decoupled from its model/runtime.
3. Whether its safety/guardrail posture is first-class or absent (if absent, fork cost ≈ rebuild).
4. Activity/maintenance signal (last release, issue velocity) — research-stage churn risk.
5. Whether local-first / offline operation is supported or assumed-cloud.

If a spike finds a permissive licence, a cleanly-decoupled Python-friendly interface layer,
and first-class safety hooks, revisit (a "fork the interface only" option could re-open) —
but the default, absent that evidence, is reference-only.
