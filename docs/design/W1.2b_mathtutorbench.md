# MathTutorBench — should Mentar use it?

Surfaced while researching alternatives to our single-judge rubric (docs/MODEL.md). Our rubric scores
*explanation quality*; it does **not** measure the thing Mentar is actually built around — **active
questioning / scaffolding** (the Help loop, probing). MathTutorBench measures exactly that.

## What it is

A published benchmark (ETH, EMNLP 2025) for evaluating LLM **tutors** (not just answer-correctness):
- **Datasets** — teacher-annotated ground truths for **7 tasks** across three skills:
  problem solving · Socratic questioning · student-solution correctness · **mistake location** ·
  **mistake correction** · **scaffolding generation** (standard + hard) · **pedagogy
  instruction-following** (standard + hard).
- **Metrics** — automatic scorers per task.
- **A 1.5B reward model** — computes *win-rates* of a tutor utterance vs the teacher ground truth
  (same spirit as our `eval/pairwise.py`). Runs on a single GPU (~10 min).
- **Runner** — `python main.py --tasks <task>.yaml --provider completion_api --model_args base_url=…`
  → **OpenAI-compatible**, so it points straight at our eval proxy. Python 3.12+; vLLM or API providers.

## Why it matters for Mentar

- It fills our biggest eval gap: **does the model SCAFFOLD (hint/ask) instead of just telling?** —
  the heart of the pedagogy engine (SPEC §12–14, the Help loop). Our reexplain rubric can't see this.
- **Mistake location / correction** map directly to the false-confidence + probe machinery (W3.4).
- External, peer-reviewed validation that our home-grown rubric isn't idiosyncratic.
- Zero new infra: it speaks the same OpenAI-compatible endpoint our harness already uses.

## Caveats (why it's a *complement*, not a replacement or a gate)

- **Licence = CC BY-SA 4.0** (copyleft). **Use as an external tool + reference only; do NOT vendor
  its code or datasets into the Mentar repo** — ShareAlike would entangle the W4.2 licence decision
  (same hard line as Hermit-AI/AGPL). Running it against our models and citing results is fine.
- **Domain/age mismatch.** General math word-problems / tutoring dialogues, **English**, age not
  specified — **not** fractions / 8–9-year-olds. So treat its scores as a **relative** signal (rank
  candidates) and a **dimension check** (can they scaffold at all?), **not** an absolute pilot gate.
- **GPU only for the reward-model tasks.** The *win-rate* tasks (scaffolding / Socratic / mistake-
  correction) load a 1.5B reward model → eval-host GPU. The **deterministic-metric tasks**
  (`student_solution_correctness`, mistake-location) run **GPU-free** — verified in the build
  container (see spike below). Python 3.12+.

## Recommendation

**Adopt as a complementary external eval, reference-only (no vendoring).** Specifically: once W1.3
narrows to the finalist(s) (currently `gemma2:9b`), run them through MathTutorBench's **scaffolding +
Socratic + mistake-location** tasks on the eval host to answer "*can the front-runner actually tutor,
not just explain?*" — a dimension our own suite is blind to.

This is the NIAH pattern again (docs/design/W1.2_eval_tooling.md): adopt a focused, validated external
tool for **one dimension**, used deterministically alongside our own T1 suite; don't fold its
(copyleft) code into Mentar.

## Hands-on spike — VERIFIED (2026-06-17)

Ran the harness end-to-end against our eval proxy from a **separate /tmp checkout** (kept outside the
Mentar tree — CC BY-SA, not vendored). Task: **`student_solution_correctness`** (12 items, MathDial
`train` slice) — chosen first because it is a **deterministic-metric task with no reward model**, so it
runs GPU-free in the build container. Model: **gemma2:9b** via the OpenAI-compatible proxy.

**Result — gemma2:9b, `student_solution_correctness` (n=12):**

| metric | value |
|---|---|
| accuracy | **0.583** |
| precision | 0.667 |
| recall | 0.333 |
| f1 | 0.444 |

Reading: the model's "is this student solution wrong?" judgement is barely above chance on this slice —
high precision but **low recall** (it misses ~⅔ of the genuinely-incorrect solutions, i.e. it tends to
wave wrong work through as "No, correct"). That is the same false-confidence failure mode our own
sycophancy suite flags, now corroborated by an external benchmark. Small n — directional, not a gate.

### Two patches were needed to run it (in the /tmp checkout ONLY — not vendored)

The upstream `completion_api` provider does **not** drive an OpenAI-compatible proxy out of the box:
1. `models/completion_api.py` `CompletionAPI.__init__`: the `else` branch (api_key present) built
   `OpenAI(api_key=…)` **without `base_url`**, so calls hit `platform.openai.com` and 401'd. Fixed to
   `OpenAI(api_key=config.api_key, base_url=config.base_url)`.
2. It defaults to the **legacy `/completions`** endpoint (`is_chat=False`); our proxy serves
   **`/chat/completions`**. Pass **`is_chat=true`** in `--model_args`.

Working invocation (run from the external checkout; token via env, never committed):
```bash
python main.py --tasks student_solution_correctness.yaml --provider completion_api \
  --model_args "base_url=$MENTAR_VLLM_BASE_URL,model=gemma2:9b,api_key=$MENTAR_VLLM_API_KEY,is_chat=true"
```
(If we upstream a fix, the `base_url`-in-else-branch bug is a clean PR; the `is_chat` default is by
design.)
