# W3.3 — BKT Cold-Start + Hinted-Win Design

Closes W3.3. Decides the mastery-update mechanism, the cold-start priors policy, and the
hinted-win discount — and pins them in code (`src/mentar/engine/bkt.py`) with invariants
T3.3 can assert.

---

## 1. The core decision — pyBKT is NOT in the per-turn hot path

W3.3's own framing says it: *"pyBKT cannot fit `learns/forgets/guess/slip` from one
learner's first sessions."* pyBKT is a **batch fit/predict** library — it learns
parameters from a dataframe of many learners' sequences. Driving it per-turn on a single
cold-start learner means refitting on a handful of rows: unstable, and a heavy/uncertain
runtime dependency in the child-facing loop (the `[⚠️ Verify pyBKT API]` flag).

**Decision.** Split the two jobs:

| Job | Mechanism | When |
|-----|-----------|------|
| **Per-turn mastery update** (hot path) | Mentar's own deterministic BKT recurrence with **hand-set priors** (`src/mentar/engine/bkt.py`) | Pilot + always |
| **Parameter fitting** (offline) | `pyBKT` fits `guess/slip/learns/forgets` from accumulated `response_log` | Post-pilot only, per skill, once **N ≥ 100** scored responses → flips `skill_state.prior_mode = 0` |

This is the standard BKT recurrence (Corbett & Anderson 1995) — fully specified below, so
the hot path has **no external ML dependency** and is unit-testable in the sandbox (no
`pip`). It also matches the schema, which already carries per-skill params + `prior_mode`.

> **⚠️ This revises the W3.3 acceptance wording** ("hinted-win mechanism … unit-tested
> *against pyBKT*"). The unit test now targets the Mentar wrapper — the thing actually in
> the loop. pyBKT verification moves to the offline-fit task (post-pilot). Flagged for
> ratification; SPEC §11 updated to match. Rationale: testing the real hot-path code beats
> testing a library we won't call per-turn.

## 2. Cold-start priors policy

Until a skill has **N ≥ 100** scored responses (post-pilot), parameters are **hand-set by
node class**, never fitted. Source of truth, in precedence order:

1. **Template `bkt_priors:`** for the node (already supported; present on all 8 pilot nodes).
2. **Node-class default** keyed by the node's `verifier.answer_type`:

| Node class (`answer_type`) | guess | slip | learns | forgets |
|----------------------------|-------|------|--------|---------|
| `mc4` (4-option multiple choice) | **0.25** | 0.10 | 0.20 | 0.00 |
| numeric (`int` / `decimal` / `fraction`, free-entry) | **0.05** | 0.10 | 0.20 | 0.00 |

*(mc4 default corrected 0.20 → 0.25 on 2026-09-02: 1/4 options, and the value all 580
shipped mc4 nodes already carry. In practice the class default is never reached — every one
of the 934 shipped nodes sets `bkt_priors:` explicitly; see §6 G1 for the real landscape.
Values are range-checked to [0,1] by `validate_template` since the same date — §6 B2.)*

- **guess** differs by class: a 4-option MC is guessable ~1/5 after eliminating distractors;
  free-numeric entry is barely guessable → 0.05.
- **forgets = 0** within-session (SPEC §11). Across-session decay is **not** applied by the
  per-turn wrapper; the `forgetting_suspect` window (W3.4) handles staleness separately.
- **Initial mastery `p_L0 = 0.10`** (prior that the child already knows a *newly-fringed*
  concept). **This matters:** the schema default `p_mastery = 0.0` is degenerate — at
  exactly 0, no correct answer can ever move mastery (`0·(1−slip)/… = 0`). The wrapper
  **seeds an uninitialised skill to `p_L0` on first update**, never updates from 0.

`forgets` is stored for forward-compat but unused in v0 (always 0).

## 3. The update (`src/mentar/engine/bkt.py`)

Two-step standard BKT per scored observation: **(a) condition on evidence, (b) apply
learning — except on a bare-wrong observation (§3.2, A20).**

```
# (a) posterior mastery given this observation
correct:    P(L|obs) = p·(1−slip)           / [ p·(1−slip) + (1−p)·guess     ]
incorrect:  P(L|obs) = p·slip               / [ p·slip     + (1−p)·(1−guess) ]

# (b) learning transition (within-session; forgets=0) — SKIPPED for bare-wrong (§3.2)
P(L') = P(L|obs) + (1 − P(L|obs))·learns
```

`P(L')` is written to `skill_state.p_mastery`; `fringe.py` reads it against the 0.85
threshold to decide advance/branch.

### 3.2 Option B — no learns credit on a bare-wrong observation (A20, ratified 2026-07-05)

**Deviation from classic BKT**, which applies step (b) after *every* observation
regardless of correctness. Mentar gates it: **any wrong** observation — hinted or not —
only runs step (a); step (b) is skipped entirely, so `P(L') = P(L|obs)` for that turn.
Correct observations, hinted or cold, still receive the `learns` credit as before.
*(Corrected 2026-09-02: this paragraph said "bare-wrong (incorrect AND unaided)" and
listed hinted-wrong as still credited — the pre-2026-08-16 rule. A20's acceptance
criterion was ratified over its body on 2026-08-16 and the code, SPEC §11 and
REMAINDER_PLAN were updated then; this doc was not. See `bkt.py` `bkt_update` and §6 G6.)*

**Why:** classic BKT's step (b) is unconditional, so a low-prior wrong-answer streak still
nudges `P(L')` upward each turn (conditioning pulls it down, learning pulls it back up, net
effect can be positive) — verified in this codebase as a 10%→21%→22% rise-then-plateau,
never false-mastering, but confusing for a parent-facing mastery percentage ("why did it go
up after they got it wrong?"). This is a symptom of the broader, well-documented **model
degeneracy** critique of vanilla BKT — parameter/update combinations that violate the
model's own conceptual meaning (e.g. a wrong answer paradoxically counting as evidence
*for* mastery): Baker, R.S.J.d., Corbett, A.T., & Aleven, V. (2008), *"More Accurate Student
Modeling through Contextual Estimation of Slip and Guess Probabilities in Bayesian Knowledge
Tracing,"* Proceedings of ITS 2008, doi:10.1007/978-3-540-69132-7_44. We did not find a
specific named "no-learning-on-incorrect" variant in the literature search conducted for
this decision — Option B is Mentar's own targeted mitigation for the degeneracy symptom we
observed, not an adopted named technique.

**SPEC §11 deviation note:** SPEC §11 describes the classic unconditional two-step update;
this file (and the code) are the source of truth for the actual Option-B-gated recurrence
Mentar implements.

### 3.1 Hinted-win discount — the mechanism

SPEC §13.2: a correct answer *after* Help is weaker evidence than a cold correct. Standard
BKT has **no native hint handling** (the corrected §11 overclaim). We implement it as an
**elevated-guess observation class** — the cleanest of the three options in §11, and exact
in our own recurrence:

```
guess_eff = guess_hinted   if (correct AND hinted)   else   guess
guess_hinted = guess + (1 − guess)·HINT_DISCOUNT          # HINT_DISCOUNT = 0.5 (default)
```

- Elevated guess **only** on a *hinted-correct* observation. A hinted-**incorrect** uses
  the normal guess (it's already strong negative evidence; we don't soften the penalty).
- With `HINT_DISCOUNT = 0.5`: MC `guess_hinted = 0.2+0.8·0.5 = 0.60`; numeric
  `0.05+0.95·0.5 = 0.525`. A hinted correct is treated as roughly a coin-flip's worth of
  evidence → it raises mastery, but markedly less than a cold correct. `HINT_DISCOUNT` is a
  single tunable constant (rationale: pedagogy team can move it; default is deliberately
  strong because over-crediting a hinted win is the dangerous direction — false confidence).

Why elevated-guess over KT-IDEM/`multigs`: KT-IDEM varies guess *per item*; we need it to
vary per *observation condition* (hinted vs not), which is a cleaner 1-line swap in our
recurrence and needs no pyBKT variant support.

### 3.3 One observation per attempt, not per re-check (2026-09-02)

The Help loop re-checks the **same item** up to `HELP_RETRY_CAP = 3` times, and each
re-check used to be a fresh BKT observation, so one item could produce four. They are not
independent: after a hint the child is on the same problem one step further in. With the
shipped numeric priors the effect is severe:

| Mastery before | one wrong | two | three | four |
|---|---|---|---|---|
| 0.84 (about to graduate) | 0.36 | 0.05 | 0.006 | 0.0006 |
| 0.70 | 0.20 | 0.03 | 0.003 | 0.0003 |

A single hard item on a bad day flattened a near-mastered skill to zero, the engine then
re-drilled it as never-learned, and the parent saw 84% → 0%.

**Rule (implemented in `_do_help_recheck_score` via `ctx.item_observed`, reset at
`PRESENT`):**

- the **first scored attempt** on an item is always an observation — hinted or not (Help
  pressed before answering makes the first re-check the observation);
- a **hinted correct** is always an observation (the resolution);
- a **hinted wrong** on an item that already produced an observation is **logged**
  (`response_log`, `hinted=1`) but **not observed**.

Max observations per item: 2. What is dropped — "one hint vs three" — is still in the log
for offline analysis, and the transfer probe at graduation is the unaided check anyway.

| Scenario | before (≤4 obs) | now (≤2 obs) | final-outcome-only (rejected) |
|---|---|---|---|
| wrong cold, right after 1 hint | ↓ then ↑ | ↓ then ↑ | ↑ only — the cold wrong is erased |
| wrong cold, right after 3 hints | ↓↓↓ then ↑, craters to ~0.01 | ↓ then ↑ | ↑ only |
| wrong cold, 3 hinted wrongs, revealed | ↓↓↓↓, 0.7 → 0.0003 | ↓ once, 0.7 → 0.2 | ↓ once |

Final-outcome-only was rejected because it credits a child *up* for a scaffolded success
after a cold wrong — inflating mastery, firing the probe early, and manufacturing exactly the
false confidence W3.4 exists to catch.

**Literature note.** The canonical convention (Corbett & Anderson's own tutors) is
*first-attempt-only*: a hinted success is never a BKT observation — "mastery means
unaided". Mentar deliberately keeps crediting a hinted correct, weakly (§3.1), because the
child-facing benefit is movement on hinted wins, while the transfer probe (`BRANCH_DECISION`
→ `PROBE_PRESENT` at ≥ 0.85) still demands an unaided pass before a node leaves the fringe.
Both halves are already built; this section only removes the correlated middle.

`recompute_mastery` replays the same rule via `prompt_ref` adjacency (an item's attempts
share `item:<id>`), so history replays stay exact.

## 4. Invariants for T3.3 (`tests/engine/test_bkt.py`) — all sandbox-runnable

1. **Hinted discount is real & strict:** from identical prior+params, `cold-correct` yields
   strictly higher `p_mastery` than `hinted-correct`.
2. **Direction:** correct raises the conditioned posterior, incorrect lowers it; output ∈ [0,1].
3. **Class priors respected:** an `mc4` node uses guess 0.20, a numeric node 0.05 (and a
   template `bkt_priors:` override wins over the class default).
4. **Seeding:** first update on an uninitialised skill starts from `p_L0=0.10`, not 0.0
   (regression guard for the degenerate-zero bug).
5. **No instant graduation:** a single hinted-correct from `p_L0` does **not** reach the
   0.85 mastery threshold (hinted wins can't graduate a concept alone).
6. **Determinism:** same inputs → same output, no RNG, no I/O.
7. **Monotone in run length:** k consecutive cold-corrects is non-decreasing, bounded
   `≤ 1.0`, and absorbing at exactly 1 (never exceeds). *(Verified numerically 2026-06-14.)*
8. **No rise on a wrong streak (A20, Option B):** k consecutive bare-wrong (unaided
   incorrect) observations from cold start never raise `p_mastery` above the running
   value — each step is `≤` the previous. Hinted-win and correct paths are unaffected.
9. **≤ 2 observations per item (§3.3):** wrong → hinted wrong → hinted right on one item
   updates the store exactly twice, and the result equals
   `bkt_update(bkt_update(P_L0, wrong), correct, hinted)`.
   *(`tests/dialogue/test_bkt_observations.py`, 2026-09-02; mutation-proved.)*
10. **First attempt is always observed, even hinted:** Help before answering, then a wrong
    re-check → one observation; a second hinted wrong → still one.

## 5. Wiring & boundaries

- **Reads** params from template `bkt_priors:` → falls back to §2 class default by
  `verifier.answer_type`. Pure function of (prior, correct, hinted, params); does **not**
  touch the DB.
- **Caller** (session loop / FSM `bkt_update` state) persists via
  `store.update_skill_state(... priors_used=True, params=<the BktParams used>)` while
  `prior_mode=1`. **Since 2026-09-02 the four parameter columns are written** on every update
  (§6 B1); rows last updated before that still hold the schema defaults, which is why
  `recompute_mastery` reads params from the curriculum, not the DB.
- **A second writer exists.** `_do_probe_classify` demotes `p_mastery` to
  `min(p, PROBE_DEMOTE_MASTERY=0.6)` on any non-clean probe — a hard clamp, not a Bayesian
  update, so the node returns to practice instead of being re-probed forever. Deliberate;
  `recompute_mastery` reproduces it. `p_mastery` is therefore "a BKT posterior, clamped by
  probes" (§6 D4).
- **Display contract (2026-09-02).** No UI surface prints `p_mastery` as a percentage.
  `web/app.py::mastery_band()` maps it to five bands whose top starts at
  `DEFAULT_MASTERY_THRESHOLD` (so "Got it" and "left the fringe" are one event) and whose
  0.60 floor is `PROBE_DEMOTE_MASTERY`; the bar keeps the continuous width. Reason: §6 G1.
- `prior_mode` flips to 0 only by the **post-pilot offline pyBKT fit** (separate task) once
  N≥100; until then `priors_used=True` always.
- Out of scope: across-session forgetting (W3.4), the proactive-probe trigger (uses the
  mastery this produces), LLM-as-judge for non-checkable items (SPEC §24).

## 6. Known gaps — what this model does NOT do

Recorded 2026-09-02 from a full trace (update → FSM callers → store → consumers → UI),
each item verified against the code. Fixed items are kept so they are not re-found.

### Fixed in the 2026-09-02 pass

- **B1 — `skill_state` parameter columns were never written.** `update_skill_state`
  upserted only `p_mastery/prior_mode/updated_at`; its docstring claimed the params were
  "set once at cold-start" and nothing did. Every row held the mc4 defaults whatever the
  node's class. Found by `recompute_mastery` disagreeing with the live engine; recorded only
  in that tool's docstring until now. **Fixed:** both writers pass `params=`; the store
  writes all four columns. Legacy rows keep their defaults until next update.
- **B2 — `bkt_priors` were not validated.** Presence only; `guess: 25` produced a posterior
  outside [0,1], the schema CHECK rejected the persist, and the child carried corrupt
  in-memory mastery. **Fixed:** `validate_template` errors on unknown keys, non-numbers, and
  values outside [0,1]; enforced repo-wide by the tests that validate every template.
- **D3 — up to four correlated observations per item.** See §3.3. **Fixed.**
- **Display printed the raw percentage** on four surfaces (mid-lesson cue, parent table,
  topic picker, progress-map hover; the progress page already banded, but at 80 not 85).
  **Fixed:** one helper, five bands, top band at the graduation threshold, legend on the
  parent page (§5).

### Recorded decisions

- **D4 — probe demote is a clamp, not an update.** See §5. Fine as a decision; written down
  so "p_mastery is a BKT posterior" is read with the caveat.
- **G6 — hinted-wrong earns no learns credit** (closed 2026-08-16, A20). A child who takes a
  hint, learns something real, and still answers wrong is credited nothing. Under-crediting
  accepted over the degeneracy it replaced (0.10 → 0.22 on a wrong-every-turn streak).

### Open — gated on pilot data, not on engineering

**G1 — no parameter has ever been fitted to learner data.** Every one of 934 nodes sets
`bkt_priors:`; the landscape as of 2026-09-02:

| Nodes | guess | slip | learns | forgets | reading |
|---|---|---|---|---|---|
| 580 | 0.25 | 0.10 | 0.20 | 0 | 4-option MC, exactly random-guess |
| 213 | 0.05 | 0.10 | 0.20 | 0 | numeric free-response |
| 107 | 0.10 | 0.10 | 0.20 | 0 | short-answer / expression |
| 11 | 0.30 | 0.15 | 0.25 | 0 | a small senior cluster |
| 10 | 0.20 | 0.10 | 0.20 | 0 | |
| 5 | 0.10 | 0.15 | 0.25 | 0 | |
| 8 | multi-line form (0.05 / 0.20) | | | | |

`guess` varies with answer *format* — sensibly. `slip = 0.10` and `learns = 0.20` are
constant across 910 of 934 nodes and `forgets = 0` across all; **nothing encodes year
level, subject, or difficulty.** `prior_mode` flips to 0 only via the post-pilot pyBKT fit
at N ≥ 100 scored responses per skill, and no pilot has run. `response_log` already
captures everything that fit needs (`learner_id, skill_id, scored, hinted, timestamp`).

*Consequence:* `p_mastery` is a sound **ordering and trend** signal (the §4 invariants).
Its **absolute value is uncalibrated** — the 0.85 graduation threshold is a chosen constant.
For *selection* this is mitigated by the two-factor graduation (BKT proposes at ≥ 0.85, the
transfer probe disposes). For *display* it was not — hence the band contract. **Never
describe the number to a parent as a probability of real mastery.**

**G5 — slip and guess are fixed, not contextual.** §3.2 cites Baker, Corbett & Aleven
(2008), whose contribution is *contextual estimation* of slip and guess. We cite it for the
degeneracy critique and adopt a different remedy; we do **not** implement that paper's
method. Cite accordingly. Needs the same data as G1.

### Open — need a design pass first

**G2 — `forgets` is declared, persisted, and never used.** `BktParams.forgets` exists, every
template sets it to 0, the DB carries `p_forgets`, and `bkt_update` never reads it
("forgets unused in v0"). Inside the model, mastery never decays.

**G3 — forgetting is handled outside BKT, by two mechanisms, on two clocks.**

| Mechanism | Location | Clock |
|---|---|---|
| stale-mastery → `FORGETTING_SUSPECT` probe | `controller.py` `STALE_MASTERY_DAYS = 14` | wall-clock days |
| spaced-review injection | `fringe.py` `REVIEW_EVERY_N = 4` | items completed |

Three notions of forgetting, no shared clock. Review cadence is **item-counted, not
interval-based**: one long session and a return after a fortnight get the same schedule.
There is no SM-2/Leitner scheduler anywhere, which is why the repo does not carry the
`spaced-repetition` topic. G2+G3 are one coherent piece of work: wire `forgets` to elapsed
time, then fold the two external mechanisms into it — after a decision on decay semantics
(mastery silently dropping between sessions is a change to design, not improvise).

**G4 — no credit transfer along the prerequisite graph.** Each skill updates in isolation;
a Year 6 success grants its Year 5 prerequisite nothing, though `select_next` walks that
same graph. A real model upgrade with research behind it; not needed for the pilot, and
getting it wrong inflates mastery.

**G7 — the graduation probe can be skipped by the session cap.** `_do_branch_decision`
checks `max_items` *before* `probe_due`. When the item that lifts a node over 0.85 is the
last of a capped session (web default 10), the node is marked mastered with **no probe**,
leaves the fringe, and is not re-selected until stale (14 days). One item in ten can
graduate unprobed, so the two-factor guarantee in G1 has a hole. Fix candidates: probe at
next session start for any ≥ 0.85 node with no `clean_pass` in `probe_event`; or check
`probe_due` before the cap. **Maintainer decision — not fixed in this pass.** The parent
legend is worded so it does not claim the probe always ran.
