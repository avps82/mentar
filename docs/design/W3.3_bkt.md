# W3.3 — BKT Cold-Start + Hinted-Win Design

Closes W3.3. Decides the mastery-update mechanism, the cold-start priors policy, and the
hinted-win discount — and pins them in code (`src/mentar/engine/bkt.py`) with invariants
T3.3 can assert.

---

## 1. The core decision — pyBKT is NOT in the per-turn hot path

W3.3's own framing says it: *"pyBKT cannot fit `learns/forgets/guess/slip` from one
learner's first sessions."* pyBKT is a **batch fit/predict** library — it learns
parameters from a dataframe of many learners' sequences. Driving it per-turn on a single
cold-start learner means refitting on a handful of rows: unstable, and a heavy/uncertain
runtime dependency in the child-facing loop (the `[⚠️ Verify pyBKT API]` flag).

**Decision.** Split the two jobs:

| Job | Mechanism | When |
|-----|-----------|------|
| **Per-turn mastery update** (hot path) | Mentar's own deterministic BKT recurrence with **hand-set priors** (`src/mentar/engine/bkt.py`) | Pilot + always |
| **Parameter fitting** (offline) | `pyBKT` fits `guess/slip/learns/forgets` from accumulated `response_log` | Post-pilot only, per skill, once **N ≥ 100** scored responses → flips `skill_state.prior_mode = 0` |

This is the standard BKT recurrence (Corbett & Anderson 1995) — fully specified below, so
the hot path has **no external ML dependency** and is unit-testable in the sandbox (no
`pip`). It also matches the schema, which already carries per-skill params + `prior_mode`.

> **⚠️ This revises the W3.3 acceptance wording** ("hinted-win mechanism … unit-tested
> *against pyBKT*"). The unit test now targets the Mentar wrapper — the thing actually in
> the loop. pyBKT verification moves to the offline-fit task (post-pilot). Flagged for
> ratification; SPEC §11 updated to match. Rationale: testing the real hot-path code beats
> testing a library we won't call per-turn.

## 2. Cold-start priors policy

Until a skill has **N ≥ 100** scored responses (post-pilot), parameters are **hand-set by
node class**, never fitted. Source of truth, in precedence order:

1. **Template `bkt_priors:`** for the node (already supported; present on all 8 pilot nodes).
2. **Node-class default** keyed by the node's `verifier.answer_type`:

| Node class (`answer_type`) | guess | slip | learns | forgets |
|----------------------------|-------|------|--------|---------|
| `mc4` (4-option multiple choice) | **0.20** | 0.10 | 0.20 | 0.00 |
| numeric (`int` / `decimal` / `fraction`, free-entry) | **0.05** | 0.10 | 0.20 | 0.00 |

- **guess** differs by class: a 4-option MC is guessable ~1/5 after eliminating distractors;
  free-numeric entry is barely guessable → 0.05.
- **forgets = 0** within-session (SPEC §11). Across-session decay is **not** applied by the
  per-turn wrapper; the `forgetting_suspect` window (W3.4) handles staleness separately.
- **Initial mastery `p_L0 = 0.10`** (prior that the child already knows a *newly-fringed*
  concept). **This matters:** the schema default `p_mastery = 0.0` is degenerate — at
  exactly 0, no correct answer can ever move mastery (`0·(1−slip)/… = 0`). The wrapper
  **seeds an uninitialised skill to `p_L0` on first update**, never updates from 0.

`forgets` is stored for forward-compat but unused in v0 (always 0).

## 3. The update (`src/mentar/engine/bkt.py`)

Two-step standard BKT per scored observation: **(a) condition on evidence, (b) apply
learning — except on a bare-wrong observation (§3.2, A20).**

```
# (a) posterior mastery given this observation
correct:    P(L|obs) = p·(1−slip)           / [ p·(1−slip) + (1−p)·guess     ]
incorrect:  P(L|obs) = p·slip               / [ p·slip     + (1−p)·(1−guess) ]

# (b) learning transition (within-session; forgets=0) — SKIPPED for bare-wrong (§3.2)
P(L') = P(L|obs) + (1 − P(L|obs))·learns
```

`P(L')` is written to `skill_state.p_mastery`; `fringe.py` reads it against the 0.85
threshold to decide advance/branch.

### 3.2 Option B — no learns credit on a bare-wrong observation (A20, ratified 2026-07-05)

**Deviation from classic BKT**, which applies step (b) after *every* observation
regardless of correctness. Mentar gates it: a **bare-wrong** observation (incorrect AND
unaided — `hinted=False`) only runs step (a); step (b) is skipped entirely, so
`P(L') = P(L|obs)` for that turn. Hinted-win, cold-correct, and hinted-wrong observations
are unaffected and still receive the `learns` credit as before.

**Why:** classic BKT's step (b) is unconditional, so a low-prior wrong-answer streak still
nudges `P(L')` upward each turn (conditioning pulls it down, learning pulls it back up, net
effect can be positive) — verified in this codebase as a 10%→21%→22% rise-then-plateau,
never false-mastering, but confusing for a parent-facing mastery percentage ("why did it go
up after they got it wrong?"). This is a symptom of the broader, well-documented **model
degeneracy** critique of vanilla BKT — parameter/update combinations that violate the
model's own conceptual meaning (e.g. a wrong answer paradoxically counting as evidence
*for* mastery): Baker, R.S.J.d., Corbett, A.T., & Aleven, V. (2008), *"More Accurate Student
Modeling through Contextual Estimation of Slip and Guess Probabilities in Bayesian Knowledge
Tracing,"* Proceedings of ITS 2008, doi:10.1007/978-3-540-69132-7_44. We did not find a
specific named "no-learning-on-incorrect" variant in the literature search conducted for
this decision — Option B is Mentar's own targeted mitigation for the degeneracy symptom we
observed, not an adopted named technique.

**SPEC §11 deviation note:** SPEC §11 describes the classic unconditional two-step update;
this file (and the code) are the source of truth for the actual Option-B-gated recurrence
Mentar implements.

### 3.1 Hinted-win discount — the mechanism

SPEC §13.2: a correct answer *after* Help is weaker evidence than a cold correct. Standard
BKT has **no native hint handling** (the corrected §11 overclaim). We implement it as an
**elevated-guess observation class** — the cleanest of the three options in §11, and exact
in our own recurrence:

```
guess_eff = guess_hinted   if (correct AND hinted)   else   guess
guess_hinted = guess + (1 − guess)·HINT_DISCOUNT          # HINT_DISCOUNT = 0.5 (default)
```

- Elevated guess **only** on a *hinted-correct* observation. A hinted-**incorrect** uses
  the normal guess (it's already strong negative evidence; we don't soften the penalty).
- With `HINT_DISCOUNT = 0.5`: MC `guess_hinted = 0.2+0.8·0.5 = 0.60`; numeric
  `0.05+0.95·0.5 = 0.525`. A hinted correct is treated as roughly a coin-flip's worth of
  evidence → it raises mastery, but markedly less than a cold correct. `HINT_DISCOUNT` is a
  single tunable constant (rationale: pedagogy team can move it; default is deliberately
  strong because over-crediting a hinted win is the dangerous direction — false confidence).

Why elevated-guess over KT-IDEM/`multigs`: KT-IDEM varies guess *per item*; we need it to
vary per *observation condition* (hinted vs not), which is a cleaner 1-line swap in our
recurrence and needs no pyBKT variant support.

## 4. Invariants for T3.3 (`tests/engine/test_bkt.py`) — all sandbox-runnable

1. **Hinted discount is real & strict:** from identical prior+params, `cold-correct` yields
   strictly higher `p_mastery` than `hinted-correct`.
2. **Direction:** correct raises the conditioned posterior, incorrect lowers it; output ∈ [0,1].
3. **Class priors respected:** an `mc4` node uses guess 0.20, a numeric node 0.05 (and a
   template `bkt_priors:` override wins over the class default).
4. **Seeding:** first update on an uninitialised skill starts from `p_L0=0.10`, not 0.0
   (regression guard for the degenerate-zero bug).
5. **No instant graduation:** a single hinted-correct from `p_L0` does **not** reach the
   0.85 mastery threshold (hinted wins can't graduate a concept alone).
6. **Determinism:** same inputs → same output, no RNG, no I/O.
7. **Monotone in run length:** k consecutive cold-corrects is non-decreasing, bounded
   `≤ 1.0`, and absorbing at exactly 1 (never exceeds). *(Verified numerically 2026-06-14.)*
8. **No rise on a wrong streak (A20, Option B):** k consecutive bare-wrong (unaided
   incorrect) observations from cold start never raise `p_mastery` above the running
   value — each step is `≤` the previous. Hinted-win and correct paths are unaffected.

## 5. Wiring & boundaries

- **Reads** params from template `bkt_priors:` → falls back to §2 class default by
  `verifier.answer_type`. Pure function of (prior, correct, hinted, params); does **not**
  touch the DB.
- **Caller** (session loop / FSM `bkt_update` state) persists via
  `store.update_skill_state(... priors_used=True)` while `prior_mode=1`.
- `prior_mode` flips to 0 only by the **post-pilot offline pyBKT fit** (separate task) once
  N≥100; until then `priors_used=True` always.
- Out of scope: across-session forgetting (W3.4), the proactive-probe trigger (uses the
  mastery this produces), LLM-as-judge for non-checkable items (SPEC §24).
